## 1. 介绍一下这个项目（题库 1）

**一句话**：这是一个面向上海的城市 POI 空间分析平台，核心是把真实 POI、行政区、人口栅格和路网放进 PostGIS，提供空间查询、行政区统计、地图瓦片、自然语言 Agent、15 分钟生活圈和多路线对比。

**展开**：

- 数据：85,864 条真实 OSM POI、16 个真实行政区、10,010,000 条合成压测数据、15,237 个人口网格、8 万多条路网边。
- 技术栈：Java 17 + Spring Boot 3.4.5 + Spring JDBC + PostgreSQL 17.11 + PostGIS 3.6.2 + pgRouting 4.0 + Redis（Memurai）+ Caffeine + GeoServer 3.0 + MapLibre。
- 四条主链路：
  1. 空间查询：周边、最近邻、缓冲区统计、行政区统计；
  2. 地图服务：动态 MVT + 预生成瓦片 + GeoServer WMS/WFS；
  3. Agent：4 个顶层意图、4 个角色、11 个工具、多轮记忆、工具轨迹和监控；
  4. 空间分析：15 分钟生活圈覆盖评估、A→B 驾车/步行多路线。
- 工程化：JWT + RBAC、Bucket4j 限流、Redis/Caffeine 两级缓存、Actuator/Prometheus、Flyway、MockMvc/Testcontainers、Docker Compose。

**面试话术**：不要一上来报技术栈，先说“它解决什么问题”，再按“数据 → 查询 → 分析 → Agent → 工程化”讲，最后给一两个实测数字。

## 2. 项目解决什么实际问题（题库 2）

**一句话**：把“地图上有哪些点”升级成四类能落地的空间决策。

**四类问题**：

1. **附近有什么**：给定坐标和半径，返回周边 POI，按距离排序，支持分类过滤。
   - 对应：`GET /api/poi/within`、`PoiService.within`。
2. **这片区域的设施怎么分布**：按行政区统计 POI 数量、分类占比。
   - 对应：物化视图 `mv_district_stats` + Redis。
3. **居民 15 分钟能不能到设施、覆盖多少人、哪里是盲区**。
   - 对应：`/api/life-circle/coverage`、`CoverageService`、`life-circle.html`。
4. **从 A 到 B 开车/步行怎么走、路上经过什么**。
   - 对应：`POST /api/route/plan`、Valhalla + 本地 pgRouting、`route.html`。

**关键点**：这四类问题分别对应“点查询、面统计、人口加权分析、路径规划”，覆盖了 GIS 后端最常见的四类能力，不是四个孤立的 Demo。

## 3. 为什么存 4326 + 4549 两列（题库 28）

**一句话**：一份负责交换和展示，一份负责米制计算。

**表结构**（`V1__init.sql`）：

```sql
geom      geometry(Point, 4326) NOT NULL,  -- WGS84：交换、展示、点面归属
geom_4549 geometry(Point, 4549)            -- CGCS2000 3 度带：单位米
```

**为什么不能只留 4326**：4326 的单位是“度”，`ST_Distance` 算出来是度数，而且不同纬度 1 度经度对应的实际距离不同，不能直接拿来和 1000 米比较。

**为什么不在查询时临时转换**：

```sql
-- 错误写法：对表列做函数运算，索引失效
ST_Distance(ST_Transform(geom, 4549), pt) < 1000
```

这会让每一行都做一次投影转换，GiST 也用不上。

**正确写法**：参数点只转一次，表列直接用预计算列。

```sql
WITH p AS (
  SELECT ST_Transform(ST_SetSRID(ST_MakePoint(?, ?), 4326), 4549) AS pt
)
SELECT ... FROM poi, p
WHERE ST_DWithin(geom_4549, p.pt, ?);
```

**两列都建 GiST**：4326 用于范围/相交/点面归属，4549 用于距离和排序。

**面试追问**：代价是存储多一列、写入时多一次转换；换来的是一定范围内的查询稳定走索引，这个交换是值得的。

## 4. 为什么用 ST_DWithin 不用 ST_Distance < x（题库 31）

**一句话**：`ST_DWithin` 能让 GiST 先做包围盒粗筛，`ST_Distance < x` 只能逐行精算。

**原理**：

- GiST 是 filter-and-refine：先用最小外接矩形（MBR）快速排除不可能命中的行，再对候选行做精确几何判断。
- `ST_DWithin(geom_4549, pt, 1000)` 可以直接利用 GiST 的距离/范围能力。
- `ST_Distance(geom_4549, pt) < 1000` 是普通表达式，数据库必须对每一行算距离后再过滤。

**实测**（10M 合成表）：

| 写法 | 计划 | 耗时 |
|---|---|---|
| `ST_DWithin` + GiST | Bitmap Index Scan | 54.6ms（冷）/ 约 22ms（热） |
| `ST_Distance < 1000` | Seq Scan | 879ms |
| 无索引 `ST_DWithin` | Parallel Seq Scan | 690ms |

**项目里的位置**：`PoiService.within`、`CoverageService`、`RoutePlanService` 的沿途 POI 统计都用 `ST_DWithin`。

**面试追问**：为什么热缓存 22ms、接口 P95 更高？因为接口还有 `ST_AsGeoJSON`、JSON 序列化、连接池和网络开销。

## 5. 10M 数据 690ms→54.6ms 怎么测的（题库 32）

**一句话**：同一张 10M 表、同一条 SQL，只改索引，用 `EXPLAIN ANALYZE` 对比计划和耗时。

**步骤**：

1. 用 `poi_bench` 生成 10,010,000 条合成点；
2. 删除 `geom_4549` 上的 GiST；
3. 执行周边查询 SQL，`EXPLAIN ANALYZE` 得到 `Parallel Seq Scan`，约 690ms；
4. 建 GiST：`CREATE INDEX idx_poi_geom_4549 ON poi_bench USING GIST (geom_4549);`
5. 同一 SQL 再测，计划变成 `Bitmap Index Scan`，约 54.6ms；
6. 连续查询后热缓存约 22ms。

**注意口径**：

- 10M 是合成数据，只用于规模压测，不能说是真实业务数据；
- 数字是本机单机、特定 SQL、特定数据集；
- 面试时说“690ms→54.6ms，计划从 Seq Scan 变 Bitmap Index Scan”，比只报数字可信。

## 6. 物化视图和普通视图区别（题库 41）

**一句话**：普通视图存 SQL，每次查都重算；物化视图存结果，查得快但需要刷新。

| | 普通视图 | 物化视图 |
|---|---|---|
| 存什么 | 查询定义 | 实际结果 |
| 查询开销 | 每次重算 | 读结果 |
| 数据新鲜度 | 实时 | 刷新后 |
| 适合 | 简单封装 | 重聚合、低频变化 |

**项目里**：`mv_district_stats` 把 16 个区的 POI 统计预聚合成 16 行，查询从 220ms 降到 0.024ms。

**刷新**：

```sql
REFRESH MATERIALIZED VIEW CONCURRENTLY mv_district_stats;
```

前提是物化视图上有唯一索引；`CONCURRENTLY` 不阻塞读，但刷新更慢、占额外空间。10M 数据全量构建约 4 分 6 秒，适合定时或低峰刷新。

## 7. 220ms→0.024ms 怎么来的（题库 42）

**一句话**：把“实时 JOIN + ST_Contains + GROUP BY”变成“读 16 行预聚合结果”。

**原来**：

```sql
SELECT d.name, p.category, count(*)
FROM poi p
JOIN district d ON ST_Contains(d.geom, p.geom)
GROUP BY d.name, p.category;
```

10M 数据下，每一行都要做点面判断和聚合，约 220ms。

**现在**：

- 物化视图预先算好 16 个区、按分类聚合；
- 查询只读 16 行；
- 再加 Redis 缓存，接口层进一步降低访问。

**面试追问**：为什么不是 0ms？因为还有 SQL 解析、网络和序列化；0.024ms 是数据库内查询耗时，不是端到端。

## 8. 有了物化视图为什么还要 Redis（题库 45）

**一句话**：物化视图减少数据库计算，Redis 减少数据库访问，是两层不同的问题。

- 物化视图：把重计算提前做掉，数据库还是要执行一次查询。
- Redis：把查询结果放在数据库外面，命中时数据库完全不参与。
- 项目做法：`DistrictService.stats` 上 `@Cacheable(value="districtStats")`，TTL 5 分钟；刷新物化视图时清理缓存。
- 项目还有 Caffeine：用于 MVT 瓦片，本地、量大、允许短时间不一致。

**面试话术**：不要把它们说成二选一，而是“计算层优化 + 访问层优化”。

## 9. MVT 为什么比 GeoJSON 小（题库 50）

**一句话**：只返回视口内的数据 + Protobuf 二进制 + 属性名只存一次。

**三个原因**：

1. **空间裁剪**：`ST_AsMVTGeom` 配合 `extent=4096`、`buffer=256`、`clip=true`，只保留当前瓦片范围。
2. **二进制编码**：Protobuf 比 JSON 文本紧凑。
3. **属性字典化**：同一属性的键名在瓦片里只出现一次，而不是每个要素重复。

**项目实测**：

- 真实数据：GeoJSON 227KB → MVT 49.7KB，降约 78.6%；
- 10M 数据：3,387KB → 856KB，降约 75%。

**代码位置**：`PoiService.tile`：

```sql
WITH bounds AS (SELECT ST_TileEnvelope(?, ?, ?) AS geom)
SELECT ST_AsMVT(q, 'poi', 4096, 'geom')
FROM (
  SELECT id, name, category,
         ST_AsMVTGeom(ST_Transform(geom, 3857), b.geom, 4096, 256, true) AS geom
  FROM poi p, bounds b
  WHERE ST_Intersects(p.geom, ST_Transform(b.geom, 4326))
  LIMIT 20000
) q;
```

**追问**：动态 MVT 每次查库，适合变化数据；预生成瓦片读磁盘，适合稳定数据和高并发，可以挂 CDN。

## 10. 为什么 COPY 到 staging（题库 60）

**一句话**：COPY 负责“快速卸货”，几何生成、校验、去重集中放在一条 `INSERT ... SELECT` 里。

**流程**（`ImportService`）：

```
上传 CSV
  → 写 import_task(PENDING)，立即返回 taskId
  → @Async("importExecutor") 后台执行
  → COPY 进 poi_staging（纯文本，最快）
  → INSERT INTO poi SELECT ... FROM poi_staging
      生成 geom / geom_4549、校验经纬度、ON CONFLICT DO NOTHING
  → 更新 SUCCESS / FAILED
```

**为什么分两步**：

- COPY 不擅长做复杂转换；
- 把转换放到 staging 之后，可以用集合操作一次性完成；
- staging 还方便做数据校验和失败排查。

**追问**：`TRUNCATE poi_staging` 当前是全局的，并发导入会互相踩，这是已知不足。

## 11. Batch 和 COPY 哪个快（题库 62）

**一句话**：这批数据里 Batch 更快，但核心结论是“批量远快于逐条”。

**5 万行实测**：

| 方式 | 耗时 |
|---|---|
| 逐条 INSERT | 14.7s |
| JDBC Batch | 6.8s |
| COPY + staging + INSERT SELECT | 9.8s |

**为什么 COPY 不是最快**：这里 COPY 只负责进 staging，后面还要多做一次“staging → 正式表”的几何转换和去重，所以总耗时被拉长。

**面试话术**：不要背“COPY 永远最快”；要区分“纯装载”和“带转换的导入”。如果只是原样入库，COPY 会更快；如果有几何生成和幂等校验，Batch 可能更合适。

## 12. Agent 整体流程（题库 67）

**一句话**：Controller 进来后，按“改写 → 意图 → 路由 → 执行 → 校验 → 汇总 → 记忆 → 轨迹”走完 11 步。

**`AgentOrchestrator.run` 顺序**：

1. 生成/读取 `sessionId`；
2. `ConversationStore.rewrite` 做追问改写；
3. `IntentRecognizer.recognize` 识别意图和实体；
4. `route(intent)` 选 `AgentType`；
5. `AgentProfiles.get` 读角色契约；
6. 组装 `AgentRequest`；
7. 调对应 `BaseAgent.run`；
8. `AnswerVerifier.verify` 校验答案；
9. `ResponseComposer.compose` 汇总；
10. `ConversationStore.append` 写回记忆；
11. `TraceStore` / `AgentMonitor` 记录轨迹和指标。

**四个角色**：

| AgentType | 角色 | 负责 |
|---|---|---|
| GENERAL | GeneralAgent | 问候、能力介绍、兜底 |
| SPATIAL_QUERY | SpatialQueryAgent | 周边/最近/统计/排名/对比 |
| ROUTE_PLANNING | RoutePlanningAgent | A→B 多路线 |
| REPORT | ReportAgent | 空间诊断报告 |

**面试话术**：重点讲“LLM 只负责理解和表达，空间计算交给确定性工具”，这是整套结构的设计原则。

## 13. 为什么只保留 4 类意图（题库 68）

**一句话**：顶层意图只负责“路由到哪个角色”，具体查询类型放到 `entities.scene`，避免意图爆炸。

**4 个顶层意图**：

- `QUERY`：查询、统计、排名、对比；
- `ROUTE`：路线规划；
- `REPORT`：诊断报告；
- `GENERAL`：问候、能力介绍、兜底。

**`entities.scene` 再细分**：

- `NEARBY`：附近有什么；
- `NEAREST`：最近的 N 个；
- `BUFFER_STATS`：缓冲区分类统计；
- `DISTRICT_STATS`：行政区统计；
- `RANKING`：行政区排名；
- `COMPARE`：两个区/两个地点对比。

**好处**：

- 意图识别简单、稳定；
- 新增查询类型只加 scene，不动顶层路由；
- 面试时能解释“为什么不是 9 类意图”——9 类会让规则和 LLM 都更难维护。

## 14. 意图怎么映射角色（题库 69）

**一句话**：一张固定路由表，4 个意图对应 4 个角色。

```java
QUERY   → SPATIAL_QUERY
ROUTE   → ROUTE_PLANNING
REPORT  → REPORT
GENERAL → GENERAL
```

**代码位置**：`AgentOrchestrator.route(IntentResult intent)`。

**为什么固定映射而不是让 LLM 选**：

- 可控、可测、可解释；
- 路由错了能通过单测和日志快速定位；
- 角色只是执行策略，不需要动态发现。

**新增角色要改什么**：`AgentType` 加枚举 → `profiles.json` 加契约 → 新建 `@Component` 继承 `BaseAgent`；Orchestrator 会自动收集并按类型注册。

## 15. 意图识别怎么做（题库 70）

**一句话**：关键词规则优先，失败了再用可选 LLM，最后统一抽实体。

**三类输入**：

1. **关键词**：如“附近/周边” → `QUERY + NEARBY`；“怎么走/路线/导航” → `ROUTE`；“报告/诊断” → `REPORT`。
2. **正则抽 from/to**：`(?:从)?(.+?)(?:到|→|->)(.+?)(?:怎么走|路线|规划|导航|的|$|[，。,.])`，所以“人民广场到外滩怎么走”和“从A到B”都能识别。
3. **可选 LLM**：只处理规则覆盖不了的边界表达；LLM 失败或超时自动回退关键词结果。

**实体抽取**：地点、分类、半径、数量、from/to。分类会做归一化，例如 LLM 说“餐厅”，库里统一成“餐饮”。

**面试追问**：为什么不让 LLM 直接判所有意图？因为关键词零成本、确定性强、可解释；LLM 适合兜底，不适合做唯一入口。

## 16. ToolRegistry 做了什么（题库 75）

**一句话**：它是 Agent 的工具网关，负责注册、白名单、参数校验、超时和统计。

**四件事**：

1. **注册**：每个工具一个 `ToolDefinition`，包含 name、description、必填参数、允许的角色。
2. **白名单**：`SpatialQueryAgent` 只能调周边类工具，`RoutePlanningAgent` 只能调 `route_compare` 等，防止角色越权。
3. **参数校验**：缺必填参数直接返回 `ToolResult.fail`，不进入业务逻辑。
4. **超时与统计**：`CompletableFuture.supplyAsync(...).get(timeout)`，超时返回失败；每次调用记录 success/error/latency。

**11 个工具**：`search_place`、`pois_within`、`nearest_pois`、`buffer_stats`、`district_stats`、`district_ranking`、`district_center`、`default_center`、`route_compare`、`list_districts`、`generate_report`（以实际注册表为准）。

**面试话术**：ToolRegistry 的价值不是“包一层方法”，而是把工具调用变成可管控、可观测的边界。

## 17. 多轮记忆怎么实现（题库 78）

**一句话**：`sessionId → ConversationState`，保存最近 12 条消息和地点/坐标/半径/分类等上下文，追问时先改写再识别。

**结构**：

- `ConversationStore`：`ConcurrentHashMap<String, ConversationState>`；
- `ConversationState`：消息列表（最多 12 条）+ `place/lon/lat/radius/category`；
- `rewrite`：判断“这是不是追问”，是就补全上下文。

**例子**：

```
用户：黄浦区各类 POI 有多少？
→ 上下文 place=黄浦区, lon/lat, category=null

用户：那餐厅呢？
→ rewrite：“在黄浦区附近 那餐厅呢 餐饮”
→ 识别为 QUERY + DISTRICT_STATS，地点仍是黄浦区
```

**项目实测**：第一个问题返回“黄浦区共有 2772 个 POI”，第二个返回“黄浦区附近 1000 米内找到 10 个餐饮 POI”。

**不足**：记忆在内存，重启丢失；生产应换 Redis + TTL。

## 18. 怎么防幻觉（题库 80）

**一句话**：三层防线——提示词约束、确定性工具、答案校验。

1. **提示词**：明确禁止编造数据，要求先调工具再回答。
2. **工具返回真实数据**：空间查询、统计、路线全部走 SQL/pgRouting/Valhalla，LLM 不参与计算。
3. **AnswerVerifier**：
   - 空答案拦截；
   - `QUERY` / `ROUTE` 这类数据意图必须至少有一次工具调用，否则判定“无证据”；
   - 检查 `NaN` / `Infinity` 等异常数值。

**边界**：这不是完整的 LLM-as-Judge，不能保证自然语言表述 100% 正确；它的目标是拦住“没调工具就编答案”和“明显异常”的情况。

**面试话术**：防幻觉不是靠一句“不要编”，而是靠“让模型没有机会算错”。

## 19. 为什么要取最大连通分量（题库 24）

**一句话**：图不连通时，`pgr_dijkstra` / `pgr_ksp` 会返回空路径，所以先把路网收敛到最大连通分量。

**项目里的路网构建**：

```
OSM 路网
  → road_raw：211,721 条边
  → 构建节点、生成 source / target
  → 取最大连通分量
  → road_main：84,203 条边
```

**为什么**：

- OSM 原始路网有断头路、孤岛、数据缺口；
- 起终点如果落在不同连通分量，最短路算法直接无解；
- 取最大连通分量后，绝大多数城市内起终点都可到达。

**追问**：取最大连通分量会丢掉一些小岛/远端路网，这是可用性和覆盖率的权衡；步行场景再通过 `road_walk_all` 做回退。

## 20. 驾车/步行路网怎么拆（题库 25）

**一句话**：不是前端切开关，而是两套表、两套过滤规则、两套成本模型。

| | `road_car` | `road_walk_v2` |
|---|---|---|
| 边数 | 81,481 | 76,824 |
| 道路过滤 | 可驾车道路 | 排除 path/track/cycleway，优先人行道/居住区 |
| 速度 | 按 maxspeed 或等级 | 1.2 m/s，台阶 0.8 m/s |
| 方向 | `oneway` 控制 | 基本无方向限制 |
| 成本 | 时间（秒） | 时间（秒），对 service/主干道加惩罚 |

**为什么不能共用一套**：

- 驾车不能走 footway/pedestrian/steps；
- 步行不能走 trunk/motorway；
- `oneway` 对车是硬约束，对行人基本无效。

**回退链**：`road_walk_v2` → `road_walk` → `road_walk_all`（全市路网，快速路/主干道加 3 倍成本）。

**面试话术**：车/人差异是数据建模问题，不是 UI 开关问题。

## 21. 生活圈解决什么问题（题库 91）

**一句话**：回答“居民 15 分钟内能不能到设施、覆盖多少人口、哪里是盲区”。

**三个输出**：

- `coverageRatio`：覆盖人口 / 总人口；
- `popCovered` / `gapPopulation`：覆盖人口和盲区人口；
- 网格 FeatureCollection：绿色覆盖、红色盲区，前端直接渲染。

**实测**：

| 区域 | 设施 | 覆盖率 | 覆盖人口 | 盲区人口 |
|---|---|---|---|---|
| 黄浦区 | 医疗 | 97.2% | 658,413 | 19,060 |
| 黄浦区 | 教育 | 76.7% | 519,353 | 158,120 |
| 浦东新区 | 医疗 | 31.9% | 1,711,833 | 3,647,388 |
| 浦东新区 | 教育 | 20.5% | 1,097,548 | 4,261,673 |

**价值**：从“附近有什么”升级到“够不够、哪里不够”，能支撑公共服务设施评估。

## 22. 人口网格怎么来的（题库 92）

**一句话**：WorldPop 2020 中国 1km 人口栅格，裁剪上海后生成 15,237 个网格，并按七普总人口校准。

**链路**：

```
WorldPop 2020 China 1km GeoTIFF
  → scripts/worldpop_to_grid.py（rasterio + numpy）
  → 裁剪上海行政区范围
  → 每个像元输出 grid_x, grid_y, lon, lat, pop
  → scripts/load_population_grid.sql
  → population_grid（15,237 个网格，9,422 个落在区内）
```

**关键处理**：

- WorldPop 像元值是“每像元人数”，按块求和，不取平均；
- 生成 4326 和 4549 两列几何；
- 用 `ST_Contains(district.geom, cell.geom)` 归属行政区；
- 按 2020 年七普 24,870,895 人统一校准。

**为什么校准**：1km 旧版是未约束估计，上海区县合计约 3,220 万，明显偏高；统一缩放不改变覆盖率。

## 23. 覆盖率怎么算（题库 94）

**一句话**：对每个网格，用 `ST_DWithin` 判断阈值半径内有没有目标设施，再按人口加权汇总。

**半径**：`radius = thresholdSeconds × 1.2 m/s`，例如 15 分钟 = 900s → 1,080m。

**SQL 骨架**（`CoverageService`）：

```sql
WITH covered AS (
  SELECT g.id,
         min(ST_Distance(p.geom_4549, g.geom_4549)) AS distance_m
  FROM population_grid g
  JOIN poi p ON ST_DWithin(p.geom_4549, g.geom_4549, ?)
  WHERE g.district_adcode = ? AND p.category = ?
  GROUP BY g.id
)
SELECT
  sum(g.pop) AS pop_total,
  sum(CASE WHEN c.id IS NOT NULL THEN g.pop ELSE 0 END) AS pop_covered,
  ...
FROM population_grid g
LEFT JOIN covered c ON c.id = g.id
WHERE g.district_adcode = ?;
```

**输出**：

- `popTotal / popCovered / coverageRatio / gapPopulation`；
- `ST_Expand(geom, cell_size_m/2/111320)` 生成网格面，返回 FeatureCollection；
- Redis 缓存键 `adcode:category:threshold`。

**追问**：为什么按人口加权而不是按格子数？因为格子人口不同，“覆盖人口/总人口”才是有业务意义的覆盖率。

## 24. 多路线怎么做的（题库 104）

**一句话**：首选 Valhalla 高精度路网，失败自动回退本地 pgRouting；两种模式各取多条候选，再做多样性去重和空间富化。

**首选 Valhalla**（`ValhallaRouteService`）：

```
POST https://valhalla1.openstreetmap.de/route
{
  "locations": [{"lat":..., "lon":...}, {"lat":..., "lon":...}],
  "costing": "auto" | "pedestrian",
  "alternates": alternatives - 1
}
```

- 解析 `trip.summary.length/time` 和 `legs[0].shape`（polyline6）；
- 8s 超时，异常/空结果返回空列表；
- 返回 `source=valhalla`、`sourceLabel=高精度路网`。

**本地兜底**（`RoutePlanService`）：

```java
List<Map<String,Object>> external = valhalla.planMode(mode, from, to, k);
return external.isEmpty() ? planMode(mode, from, to, k) : external;
```

- `pgr_ksp` 取 K+2 条候选；
- 按边集合 Jaccard 相似度 > 0.8 判重；
- 最多 3 条驾车 + 3 条步行；
- 按耗时排序，第一条标“最快/推荐”。

**实测（人民广场→外滩）**：

| 模式 | 距离 | 时间 | 路线数 |
|---|---|---|---|
| 驾车 | 2.9km | 11 分钟 | 3 |
| 步行 | 2.0km | 27 分钟 | 3 |

**追问**：为什么接外部服务？自建路网只是 OSM 子集，`maxspeed/oneway` 缺失多；Valhalla 用完整 OSM 和成熟代价模型。外部只负责几何/距离/时间，沿途富化仍用本地 PostGIS。

## 25. 沿途特点怎么算（题库 105）

**一句话**：用路线几何做 150m 缓冲，统计 POI 分类；再叠加道路类型和行政区，拼成一句话摘要。

**具体**：

1. **距离**：`sum(length_m)`；
2. **时间**：`sum(cost)`，cost 已按车速/步速换算成秒；
3. **道路构成**：按 `highway` 分组求长度占比（Valhalla 路线缺省，只对本地路线有）；
4. **沿途 POI**：

```sql
SELECT p.category, count(*) AS cnt
FROM poi p, route r
WHERE ST_DWithin(p.geom_4549, r.geom_4549, 150)
GROUP BY p.category
ORDER BY cnt DESC
LIMIT 5;
```

5. **行政区**：`ST_Intersects(district.geom, route_geom)`；
6. **摘要**：由以上真实统计拼出来，例如“全程 2.9 公里，预计驾车 11 分钟；沿途餐饮 50 个，穿过黄浦区”。

**追问**：这是启发式统计，150m 缓冲不等于真实“沿途体验”；但比只返回一条线更有解释性。

## 26. 为什么路线时间是估算（题库 106）

**一句话**：没有实时路况、红绿灯和转向限制数据，只能用标称速度或历史速度估算。

**具体原因**：

- Valhalla 的 `auto` 用路网标称速度，不接实时交通；
- 本地路网 `maxspeed` 大量为空，用默认车速；
- 没有信号灯等待、拥堵、施工、限行；
- `oneway` 在 OSM 里也可能缺失。

**面试话术**：明确说“这是路线规划演示，不是生产导航”；如果要生产级，需要实时交通数据、转向限制、历史速度模型，并自建 Valhalla/OSRM。

## 27. 项目最大难点（题库 121）

**一句话**：六个真实坑，每个都有对应的解决方式。

1. **坐标系单位错误**：最早在 4326 上算距离，得到的是“度”；后来改为 4549 米制列。
2. **10M 全表扫描**：`EXPLAIN` 发现 Seq Scan；改 `ST_DWithin` + GiST，690ms→54.6ms。
3. **路网不连通**：`pgr_dijkstra` 返回 0 条边；取最大连通分量，再做步行回退。
4. **GeoServer 多几何列 BBox 混用**：预览空白；发布单几何列视图或手动修 BBox。
5. **LLM 分类不一致**：LLM 说“餐厅”，库里是“餐饮”；用 `normalizeCategory` 归一化。
6. **Agent 工具循环**：LLM 反复调同一工具；限制最多 2 轮、提示词约束、确定性路径兜底。

**面试话术**：挑 2–3 个讲深，不要报流水账；重点讲“怎么发现 → 怎么定位 → 怎么验证”。

## 28. 项目有哪些不足（题库 127）

**一句话**：如实说边界，比硬吹更加分。

- **记忆在内存**：会话重启丢失，生产换 Redis + TTL；
- **生活圈用欧氏半径**：不是路网等时圈，下一步 `pgr_drivingDistance`；
- **人口 1km 较粗**：更高精度换 WorldPop 100m constrained；
- **步行路网会回退**：不连通时回退全市路网，并标注；
- **并发导入 staging 全局清空**：并发会互相踩，生产按 taskId 隔离；
- **压测是单机 50 并发**：不代表生产容量；
- **权限用户是内存演示账号**：未接数据库/LDAP；
- **Valhalla 用公共实例**：可能限流，生产需自建。

**面试话术**：每条不足后面跟一句“下一步怎么做”，展示工程判断，而不是自我否定。

## 29. Agent 秒回是不是没调用（题库 136）

**一句话**：不是没调用，而是空间查询走的是确定性 SQL 工具，本来就只有 20ms 级。

**证据**：

- `steps` 里能看到工具名、输入、输出、耗时；
- `toolsUsed` 显示实际调用的工具，例如 `default_center`、`pois_within`；
- `engine` 显示 `rule/tool` 或 `llm`；
- `latencyMs` 显示真实耗时；
- `GET /api/agent/trace/{requestId}` 能查完整工具轨迹。

**实测**：周边问答约 22ms，调用 2 个工具；`AgentMonitor` 记录请求数、成功率、平均耗时和各角色调用数。

**面试话术**：LLM 只负责理解与表达；数据类问题不经过 LLM 计算，所以快是设计目标，不是“没调用”。

## 30. 限流怎么做（题库 114）

**一句话**：Bucket4j 令牌桶，按 IP 限制每分钟 120 次，超限返回 429。

**实现**：

- `RateLimitConfig` 创建 Bucket，容量 120，周期 1 分钟；
- 过滤器从请求取 IP，尝试消费 1 个令牌；
- 失败直接返回 429，不进入业务逻辑；
- 配置项：`rate-limit.enabled/capacity/period-minutes`。

**实测**：连续 125 次请求，约 99 次返回 429，说明令牌桶生效。

**不足**：令牌桶在 JVM 内存，多实例部署时每台各自限流；生产应把桶状态放 Redis，或用网关统一限流。

## 最后：30 题怎么背

1. **先背骨架**：每题只记“一句话 + 3 个关键词”。
2. **再补项目细节**：数字、SQL、类名各记一个，足够撑住追问。
