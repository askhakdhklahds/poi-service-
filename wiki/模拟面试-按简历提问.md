## 开场 · 2 分钟项目介绍

**面试官：先简单介绍一下这个项目，重点讲你负责的部分。**

> 我做的是一个城市 POI 空间分析平台，解决“附近有什么、某个区域的设施怎么分布、居民 15 分钟内能不能到、从 A 到 B 怎么走”这几类问题。
>
> 数据侧导入了 85,864 条真实上海 OSM POI 和 16 个真实行政区，另外用 1000 万条合成数据做规模压测。核心设计是 4326 存储 + 4549 米制投影的双列坐标模型，两个几何列都建了 GiST 索引。
>
> 查询侧周边用 `ST_DWithin`，因为能走 GiST 包围盒预筛；最近邻用 `<->` KNN。10M 数据上 `ST_DWithin` 从无索引的 690ms 优化到 54.6ms，KNN 0.37ms。
>
> 统计侧用物化视图把行政区聚合从 220ms 降到 0.024ms，再叠 Redis，接口命中约 25ms。
>
> 地图侧用 `ST_AsMVT` 出矢量瓦片，真实数据同范围从 GeoJSON 227KB 降到 49.7KB；同时提供预生成瓦片和 GeoServer 的 WMS/WFS。
>
> Agent 侧我参考 EchoMind 的结构做了精简重构：Orchestrator 负责意图、路由、执行、校验、汇总；四个角色分别处理通用问答、空间查询、路线规划和报告；工具通过 ToolRegistry 做白名单、超时和统计；LLM 只负责理解和表达，空间计算全部交给确定性 SQL 工具。
>
> 最近还加了 15 分钟生活圈：WorldPop 人口落到 1km 网格，按七普人口校准，算覆盖率和盲区；以及 A→B 多路线，首选 Valhalla 高精度路网，失败回退本地 pgRouting。
>
> 整体是 Spring Boot 3 + PostGIS + Redis + Docker Compose，能部署、能监控、能测试。

## 第一轮 · 数据与查询

### Q1. 4326 和 4549 分别是什么？为什么存两份？

**面试官：你简历写“4326 存储 + 4549 米制投影的双列模型”，这两个分别是什么？为什么不能只留一个？**

> 4326 是 WGS84 经纬度坐标系，单位是度，负责数据交换、前端展示和点面归属；4549 是 CGCS2000 3 度带高斯-克吕格投影，中央经线 120°E，单位是米，负责距离、面积和范围计算。
>
> 只留 4326 的话，`ST_Distance` 算出来是“度”，不能直接和 1000 米比较，而且不同纬度 1 度经度对应的实际距离不一样；只留 4549 的话，跨系统交换、GeoJSON 输出和前端使用都不方便。所以一份负责交换，一份负责计算。

**追问：为什么上海用 4549，不用 3857？**

> 3857 是 Web 墨卡托，单位虽然也是米，但它是为全球地图切片设计的，面积和距离在高纬度会明显变形。4549 是上海所在 3 度带的本地投影，在这个范围内距离精度更适合做空间分析。

### Q2. 为什么不能在查询时 ST_Transform，而要多存一列？

**面试官：多存一列不是浪费吗？查询时转一下不行吗？**

> 不行，主要两个原因。
>
> 第一，`ST_Transform` 是逐行计算，10M 数据每行都转一次，开销很大。
>
> 第二，更关键的是索引。对表列做 `ST_Transform(geom, 4549)` 之后，数据库没法直接用 `geom` 上的 GiST 索引，等于退化成全表扫描。
>
> 正确做法是只转参数点一次：`WITH p AS (SELECT ST_Transform(ST_SetSRID(ST_MakePoint(?, ?), 4326), 4549) AS pt)`，表列直接用预计算的 `geom_4549`，这样索引能正常用。代价是存储多一列、写入时多一次转换，这个交换是值得的。

---

### Q3. GiST 是什么？为什么能让 ST_DWithin 变快？

**面试官：你提到 GiST 索引，能讲讲 GiST 是什么、为什么能加速空间查询吗？**

> GiST 是通用搜索树，PostGIS 用它来实现类似 R 树的空间索引。它的核心是 filter-and-refine：每个节点存子节点的最小外接矩形 MBR，查询时先用 MBR 快速排除不可能命中的分支，再对少量候选做精确几何判断。
>
> `ST_DWithin(geom_4549, pt, 1000)` 能利用这个结构先做范围粗筛；而 `ST_Distance(geom_4549, pt) < 1000` 是普通表达式，数据库只能对每一行先算距离再过滤，用不上索引。
>
> 项目里 10M 数据实测：`ST_DWithin` + GiST 是 54.6ms，计划是 Bitmap Index Scan；`ST_Distance < 1000` 是 879ms，计划是 Seq Scan；同样的 `ST_DWithin` 如果删掉索引，会变成 Parallel Seq Scan，约 690ms。

**追问：为什么热缓存是 22ms，接口 P95 却更高？**

> 22ms 是数据库内、数据已经在 shared buffers 里的查询耗时。接口还要做 `ST_AsGeoJSON`、JSON 序列化、连接池取连接和网络传输，所以端到端会更高。我简历里写的数字都注明了是数据库查询还是接口耗时，不会混着说。

### Q4. 690ms→54.6ms 怎么证明是索引的功劳？

**面试官：你怎么证明这个提升是索引带来的，而不是缓存、数据量或者机器状态变化？**

> 我控制了三件事：同一张 10M 表、同一条 SQL、同一个数据库实例；只改变“有没有 GiST 索引”这一个变量。
>
> 步骤是：先删掉 `geom_4549` 上的索引，`EXPLAIN ANALYZE` 看到 Parallel Seq Scan，约 690ms；然后建 GiST，再跑同一条 SQL，计划变成 Bitmap Index Scan，约 54.6ms；之后连续查询得到热缓存约 22ms。
>
> 所以冷查询的 690→54.6 是索引和计划变化带来的；22ms 是加上缓存后的结果，我在简历里把两个口径分开了。

---

### Q5. KNN 的 <-> 为什么能 0.37ms？

**面试官：你简历写最近邻 0.37ms，KNN 是怎么做到的？**

> 用的是 `ORDER BY geom_4549 <-> pt LIMIT N`。`<->` 是 GiST 的距离排序算子，索引本身按距离组织，数据库可以从最近的分支开始读，读到够 N 条就停，不需要全表排序。
>
> 项目里的 `PoiService.nearest` 就是这个写法。10M 数据上只读最近 N 行，所以是 0.37ms 级别，`EXPLAIN` 能看到 Index Scan。

**追问：为什么 within 不用 <->，而 nearest 用？**

> `within` 已经用半径过滤了，结果集有限，按精确距离 `distance_m` 排序更直观；`nearest` 不设半径，如果先过滤再排序就得扫很多行，用 `<->` 直接走 KNN 索引取最近 N 个更合适。

---

### Q6. 为什么用 PostGIS，不用 MySQL 空间函数或 Elasticsearch？

**面试官：这些功能 MySQL 也能做，为什么选 PostGIS？**

> 主要看空间分析的完整度和精度。
>
> 第一，PostGIS 的函数覆盖更全：`ST_DWithin`、`ST_Contains`、`ST_Intersects`、`ST_AsMVT`、`ST_TileEnvelope`、`ST_Transform`、`ST_AsMVTGeom`，还有 pgRouting 的图算法。
>
> 第二，坐标系和投影支持更成熟。我有 4326 和 4549 双列，需要可靠的投影转换和米制计算。
>
> 第三，PostGIS 和 PostgreSQL 的 GiST、物化视图、`EXPLAIN` 配合得很好，优化手段透明。
>
> Elasticsearch 的 geo 查询适合搜索场景，但做缓冲区统计、点面归属、MVT 瓦片、路网算法不如 PostGIS 直接。这个项目是空间分析为主，所以 PostGIS 更合适。

## 第二轮 · 缓存、地图与导入

### Q8. 物化视图和普通视图有什么区别？

**面试官：你简历写物化视图把 220ms 降到 0.024ms，先说说物化视图和普通视图的区别。**

> 普通视图只保存 SQL 定义，每次查询都重新执行；物化视图保存实际结果，查询时直接读结果，所以快，但数据是刷新时的快照。
>
> 项目里 `mv_district_stats` 把 16 个区的 POI 统计预聚合成 16 行。原来实时 `JOIN district + ST_Contains + GROUP BY` 在 10M 数据上约 220ms，查物化视图约 0.024ms。

**追问：物化视图算不算“作弊”？**

> 不算，这是典型的空间预聚合。行政区统计变化频率低，适合预计算；代价是刷新慢，10M 数据全量构建约 4 分 6 秒，所以我用 `REFRESH MATERIALIZED VIEW CONCURRENTLY` 在低峰刷新，并且要求物化视图上有唯一索引。

---

### Q9. 有了物化视图，为什么还要 Redis？

**面试官：物化视图已经很快了，为什么还要加 Redis？**

> 因为它们解决的是两层不同的问题：物化视图减少数据库计算，Redis 减少数据库访问。
>
> 物化视图再快，每次请求还是要进数据库、解析 SQL、走连接；Redis 命中时数据库完全不参与。项目里 `DistrictService.stats` 用 `@Cacheable(value="districtStats")`，TTL 5 分钟，接口冷启动约 58ms、Redis 命中约 25ms。
>
> 另外 MVT 瓦片用 Caffeine 而不是 Redis，因为瓦片体积大、访问频繁、允许短时间不一致，放本地更合适。

---

### Q10. Redis 缓存一致性怎么保证？

**面试官：物化视图刷新了，Redis 里还是旧数据怎么办？**

> 现在用的是短 TTL + 主动清理：统计缓存 TTL 5 分钟；刷新物化视图时清对应缓存；导入新数据后也提示刷新或等 TTL 过期。
>
> 这是最终一致，不是强一致。这个场景对实时性要求不高，5 分钟延迟可以接受。如果要更强，可以用“刷新成功后发布事件删缓存”，或者把版本号放进缓存键。

**追问：缓存穿透、空值怎么处理？**

> 配置了 `cache-null-values: false`，不缓存空结果；不存在的行政区或分类直接返回 400，不会把空值写进缓存。

---

### Q11. MVT 为什么比 GeoJSON 小？

**面试官：你简历写 MVT 从 227KB 降到 49.7KB，为什么小这么多？**

> 三个原因：只返回视口内数据、二进制编码、属性名只存一次。
>
> 具体做法是 `ST_TileEnvelope` 算瓦片范围，`ST_Intersects` 用 4326 GiST 粗筛，`ST_AsMVTGeom` 转瓦片坐标并裁剪，`ST_AsMVT` 编码成 Protobuf。参数是 `extent=4096`、`buffer=256`、`clip=true`。
>
> 真实数据同范围 GeoJSON 227KB，MVT 49.7KB，降了 78.6%；10M 数据从 3,387KB 降到 856KB，降约 75%。

**追问：动态瓦片和预生成瓦片怎么选？**

> 动态 MVT 每次查库，适合数据经常变、按分类过滤的场景，我用 Caffeine 缓存 `z/x/y/category`；预生成 `.pbf` 读磁盘，适合稳定数据和高并发，可以挂 CDN，设 7 天缓存。项目两种都提供了。

### Q12. GeoServer 怎么发布？多几何列的坑是什么？

**面试官：你提到 GeoServer WMS/WFS，具体怎么发布？遇到过什么问题？**

> 通过 REST 创建 workspace `poi`、PostGIS datastore `poi_pg`，然后发布 `poi:poi` 和 `poi:district` 图层，设置 SRS 和 BBox，再预览。
>
> 遇到的坑是：`poi` 表有 `geom` 和 `geom_4549` 两个几何列，GeoServer 可能把 BBox 混用到 4549 上，导致预览空白或范围不对。解决方式是发布只包含单个几何列的视图，或者手动修正 BBox。

**追问：WMS、WFS、WMTS 区别？**

> WMS 返回渲染好的图片；WFS 返回矢量要素，可以做查询和编辑；WMTS 返回预切好的瓦片，适合高并发底图。项目里 WMS/WFS 走 GeoServer，矢量瓦片走自己的 MVT 接口。

### Q13. 异步导入的完整流程？

**面试官：你简历写 CSV 异步导入，讲讲从上传到入库的完整流程。**

> 上传后先写 `import_task`，状态 PENDING，立即返回 taskId；后台用 `@Async("importExecutor")` 执行。
>
> 第一步 `COPY` 把 CSV 快速写进 `poi_staging`；第二步一条 `INSERT INTO poi SELECT ... FROM poi_staging`，在里面生成 `geom` 和 `geom_4549`、校验经纬度、用 `ON CONFLICT (source_id) DO NOTHING` 做幂等；最后更新任务为 SUCCESS 或 FAILED。前端轮询 `/api/import/tasks/{id}` 看进度。

**追问：为什么要先进 staging？**

> COPY 擅长快速卸货，不擅长复杂转换；把几何生成、校验、去重集中到一条集合操作里，既快又好排查。staging 还可以保留原始数据，失败时能定位是哪一行。

---

### Q14. 三种导入方式为什么 COPY 不是最快？

**面试官：你简历写逐条 14.7s、Batch 6.8s、COPY 9.8s，为什么 COPY 反而比 Batch 慢？**

> 因为这里的 COPY 只负责进 staging，后面还要多做一次“staging → 正式表”的转换和去重，总耗时被拉长了。
>
> 5 万行实测：逐条 INSERT 14.7s，JDBC Batch 6.8s，COPY + staging + INSERT SELECT 9.8s。
>
> 结论不是“COPY 永远最快”，而是“批量远快于逐条”。如果只是原样装载、没有转换，COPY 会更快；带几何生成和幂等校验时，Batch 可能更合适。我如实写这个结果，而不是硬套结论。

---

### Q15. 线程池参数怎么定？拒绝策略呢？

**面试官：导入线程池 core、max、queue 怎么配？任务满了怎么办？**

> 现在是 `importExecutor` core 2、max 4、queue 50。导入是 IO/数据库密集型，线程开太多会抢数据库连接和磁盘，所以配置比较保守。
>
> 拒绝策略目前是默认的 AbortPolicy，第 55 个任务会抛 `TaskRejectedException`。生产上我会改成 CallerRuns 或者把任务持久化后重试，并加监控。

**追问：并发导入有什么问题？**

> 当前 `TRUNCATE poi_staging` 是全局的，两个导入同时跑会互相踩。这是已知不足，生产应该按 taskId 隔离 staging，或者加锁串行化。

## 第三轮 · Agent

### Q16. Agent 的整体流程？

**面试官：你简历写 EchoMind 风格的分层 Agent，先讲讲一次请求的完整流程。**

> `AgentOrchestrator` 里是 11 步：生成/读取 sessionId → 追问改写 → 意图识别 → 选择 AgentType → 读角色契约 → 组装请求 → 调对应 Agent → 答案校验 → 响应汇总 → 写回记忆 → 记录轨迹和监控。
>
> 四个角色：GENERAL 处理问候和兜底，SPATIAL_QUERY 处理周边/最近/统计/排名/对比，ROUTE_PLANNING 处理 A→B 路线，REPORT 处理诊断报告。
>
> 核心原则是：LLM 只负责理解和表达，空间计算全部交给确定性 SQL 工具。

---

### Q17. 为什么只保留 4 类意图？

**面试官：查询场景明明有很多种，为什么顶层只留 4 类意图？不会不够用吗？**

> 顶层意图只负责“路由到哪个角色”，具体查询类型放在 `entities.scene` 里。
>
> 4 个顶层意图是 QUERY、ROUTE、REPORT、GENERAL；QUERY 内部再用 scene 区分 NEARBY、NEAREST、BUFFER_STATS、DISTRICT_STATS、RANKING、COMPARE。
>
> 如果顶层做 9 类，规则和 LLM 都更难维护，新增一种查询就要改意图体系；现在新增查询只加 scene，不动路由，识别也更稳定。

---

### Q18. 意图识别怎么做？为什么不让 LLM 全权判断？

**面试官：意图识别具体怎么实现？为什么不让大模型直接判断所有意图？**

> 关键词规则优先，识别不了再用可选 LLM，最后统一抽实体。
>
> 比如“附近/周边”走 QUERY+NEARBY，“怎么走/路线/导航”走 ROUTE，“报告/诊断”走 REPORT；地点、分类、半径、数量、from/to 用规则和正则抽。from/to 的正则支持“从A到B”“A到B”“A→B”三种写法。
>
> 不让 LLM 全权判断，是因为关键词确定性强、零成本、可解释、容易测试；LLM 适合兜底边界表达，而且失败时可以回退关键词结果。

---

### Q19. profiles.json 是干什么的？

**面试官：你简历写 AgentProfiles 和 profiles.json，为什么要单独放配置文件？**

> 它存放每个角色的契约：mission、workflow、工具范围、是否启用 LLM、温度等。角色差异配置化，Orchestrator 启动时自动收集并按 AgentType 校验，缺角色会报错。
>
> 好处是新增角色只改三处：AgentType 加枚举、profiles.json 加契约、新建一个 `@Component` 继承 BaseAgent；不用改编排逻辑。

### Q20. ToolRegistry 做了什么？

**面试官：你简历写 11 个工具，工具调用是怎么管控的？**

> ToolRegistry 是工具网关，做四件事：注册、角色白名单、必填参数校验、超时和统计。
>
> 每个工具声明允许哪些角色调用，比如 ROUTE_PLANNING 只能用 `route_compare` 和 `nearest_pois`，防止越权；缺必填参数直接返回失败，不进业务；执行用 `CompletableFuture.get(timeout)`，超时返回 `ToolResult.fail`，不会让整个请求 500；每次调用记录 success/error/latency，供 trace 和监控使用。

---

### Q21. 多轮记忆怎么实现？“那餐厅呢”怎么接上？

**面试官：Agent 怎么记住上下文？用户只说“那餐厅呢”，怎么知道在问哪里？**

> 用 `sessionId → ConversationState`，每个会话保存最近 12 条消息，以及 place、lon、lat、radius、category 这些上下文。
>
> 请求进来先做改写：如果问题是追问词，就补上上下文。比如上一轮问“黄浦区各类 POI 有多少”，下一轮“那餐厅呢”会被改写成“在黄浦区附近 那餐厅呢 餐饮”，再走意图识别。
>
> 实测第一个问题返回“黄浦区共 2772 个 POI”，第二个返回“黄浦区附近 1000 米内 10 个餐饮 POI”。

**追问：记忆为什么放内存？**

> 演示够用，但重启会丢。生产应该换 Redis + TTL，并按用户隔离。

---

### Q22. 怎么防幻觉？

**面试官：LLM 很容易编数据，你怎么保证 Agent 不胡说？**

> 三层：提示词约束、确定性工具、答案校验。
>
> 提示词明确要求先调工具再回答、不许编数据；空间查询、统计、路线全部走 SQL / pgRouting / Valhalla，LLM 不参与计算；最后 `AnswerVerifier` 检查空答案、数据类意图有没有工具调用证据、有没有 NaN/Infinity。
>
> 比如 QUERY 和 ROUTE 如果一次工具都没调，会被判定“无证据”并拦截。

**追问：这算 LLM-as-Judge 吗？**

> 不算。它是规则校验，只能拦住明显问题，不能保证自然语言表述 100% 正确。完整评测需要 LLM-as-Judge 或人工标注，这是下一步。

---

### Q23. 为什么只有 GENERAL 开 LLM？

**面试官：既然用了 Agent，为什么空间查询不让 LLM 生成 SQL 或直接算？**

> 因为正确性和可复现性。距离、缓冲区、排名、路线这些计算，LLM 很容易算错或编坐标；而 SQL 是确定的，同样的输入永远同样的输出，还能用 `EXPLAIN` 和单测验证。
>
> 所以 LLM 只处理问候、能力介绍和规则覆盖不了的兜底；查询、路线、报告走确定性路径。这个配置可以在 profiles.json 里改，但改之前要有回归测试。

---

### Q24. Agent 秒回，是不是根本没调用？

**面试官：我看你演示时 Agent 20 多毫秒就回了，真的调模型或工具了吗？**

> 调了工具，但没有调 LLM。空间查询走的是确定性 SQL 工具，本来就只有 20ms 级。
>
> 页面上能看到 `intent`、`agentType`、`engine`、`toolsUsed`、`latencyMs`，执行轨迹里能看到工具名、输入、输出和耗时；还可以通过 `/api/agent/trace/{requestId}` 查完整轨迹。周边问答实测约 22ms，调用了 `default_center` 和 `pois_within` 两个工具。

---

### Q25. Agent 怎么观测？

**面试官：线上怎么知道 Agent 有没有问题？**

> 三层：响应里的 `steps` 记录每次工具调用；`TraceStore` 按 requestId 存最近 200 条轨迹；`AgentMonitor` 统计请求数、成功率、平均耗时和各角色调用次数。
>
> 另外 Actuator/Prometheus 暴露指标，日志里能按 requestId 串起来。

---

## 第四轮 · 生活圈与多路线

### Q26. 生活圈解决什么问题？

**面试官：你简历写 15 分钟生活圈，这个功能到底回答什么问题？**

> 回答三个问题：居民 15 分钟内能不能到设施、覆盖多少人口、哪里是盲区。
>
> 输出覆盖人口、覆盖率、盲区人口，以及一个网格 FeatureCollection，绿色是覆盖、红色是盲区，前端直接渲染。这把项目从“附近有什么”升级成了“设施够不够、哪里不够”。

---

### Q27. 人口网格怎么来的？为什么校准？

**面试官：WorldPop 数据具体怎么处理？为什么要校准人口？**

> 用 WorldPop 2020 中国 1km 人口栅格，`worldpop_to_grid.py` 裁剪上海后生成 15,237 个网格，其中 9,422 个落在行政区内。
>
> 每个像元的值是“每像元人数”，按块求和，不取平均；生成 4326 和 4549 两列几何；用 `ST_Contains(district.geom, cell.geom)` 归属到区。
>
> 校准是因为 1km 旧版是未约束估计，上海区县合计约 3,220 万，明显偏高。我按 2020 年七普 24,870,895 人统一缩放。统一缩放不改变覆盖率，只校准人口绝对值。

---

### Q28. 覆盖率怎么算？盲区怎么找？

**面试官：覆盖率的具体口径是什么？**

> 半径 = 步行时间 × 1.2 m/s，比如 15 分钟 = 900 秒 = 1,080 米。
>
> 对每个网格，用 `ST_DWithin(poi.geom_4549, grid.geom_4549, radius)` 判断阈值内有没有目标设施；有就是覆盖，没有就是盲区。最后按人口加权汇总：覆盖率 = 覆盖人口 / 总人口，不是覆盖格子数 / 总格子数。
>
> 盲区就是 `covered=false` 且人口大于 0 的网格，前端画成红色。结果 Redis 缓存，键是 `adcode:category:threshold`。

**追问：为什么黄浦 97.2%，浦东只有 31.9%？**

> 黄浦面积小、医疗设施密集；浦东面积大、设施分布不均，很多人口网格离医院超过 1,080 米。这是模型算出来的结果，不是官方统计，我会明确说口径和局限。

---

### Q29. 多路线怎么做的？

**面试官：你简历写多路线对比，具体怎么实现？**

> 首选 Valhalla 高精度路网，失败自动回退本地 pgRouting。
>
> Valhalla 侧用 `costing=auto` 或 `pedestrian`，带 `alternates` 备选，解析 `summary` 和 polyline6 几何，8 秒超时；异常或空结果就回退本地。
>
> 本地侧用 `pgr_ksp` 取多条候选，按边集合 Jaccard 相似度大于 0.8 去重，最多 3 条驾车 + 3 条步行，按耗时排序后第一条标“最快/推荐”。
>
> 人民广场到外滩实测：驾车 2.9km / 11 分钟，步行 2.0km / 27 分钟，各 3 条。

**追问：为什么要接外部服务？**

> 自建路网只是上海 OSM 的一个子集，`maxspeed` 和 `oneway` 缺失多，路线会贴直线或绕行不自然。Valhalla 用完整 OSM 和成熟代价模型，路线质量更好。外部只负责几何、距离、时间，沿途 POI 和行政区仍然用本地 PostGIS 算。

---

### Q30. 为什么用 pgr_ksp，不用多次 pgr_dijkstra？

**面试官：多路线为什么选 KSP？**

> KSP 一次能返回 K 条候选路径，不需要自己反复禁边再跑最短路；然后我用边集合 Jaccard 去掉太相似的，保证方案有差异。
>
> 如果自己跑多次 Dijkstra，每次都要改图或禁边，逻辑复杂、性能也差。

---

### Q31. 车/人路网怎么区分？

**面试官：驾车和步行是前端切换，还是后端两套数据？**

> 后端两套数据，不是前端开关。`road_car` 只保留可驾车道路，按 maxspeed 或等级算时间，`oneway` 控制方向；`road_walk_v2` 排除 path/track/cycleway，优先人行道和居住区道路，速度 1.2 m/s，台阶 0.8 m/s。
>
> 步行不连通时逐级回退 `road_walk` → `road_walk_all`，并标注“路网回退”。

---

### Q32. 沿途特点怎么算？

**面试官：路线旁边有什么，你怎么算出来的？**

> 用路线几何做 150 米缓冲，统计 POI 分类；再用 `ST_Intersects` 算经过哪些行政区；叠加距离、时间、道路类型构成，拼成一句话摘要。
>
> 比如“全程 2.9 公里，预计驾车 11 分钟；沿途餐饮 50 个，穿过黄浦区”。
>
> 这是启发式统计，150 米缓冲不等于真实沿途体验，但比只返回一条线更有解释性。

---

### Q33. 为什么路线时间是估算？

**面试官：你给的时间能当导航用吗？**

> 不能，这是估算。没有实时路况、红绿灯等待、转向限制和施工限行；Valhalla 用标称速度，本地 `maxspeed` 也大量为空。
>
> 我会明确说它是路线规划演示，不是生产导航。生产级需要实时交通、历史速度模型和转向限制，并自建 Valhalla/OSRM。

---

## 第五轮 · 工程化

### Q34. JWT 怎么工作？RBAC 怎么设计？

**面试官：你简历写 JWT + RBAC，具体怎么做的？**

> 登录时校验用户名密码，签发 JWT，里面带用户名、角色和过期时间，默认 120 分钟；请求带 `Authorization: Bearer token`，过滤器解析并校验签名和过期时间，是无状态认证。
>
> RBAC 有三个角色：admin、analyst、viewer。`/api/admin/**` 要求 ADMIN，`/api/import/**` 要求 ADMIN 或 ANALYST，读接口公开。实测未带 token 访问 admin 接口返回 403，带 admin token 返回 200。

---

### Q35. 限流怎么做？

**面试官：接口怎么防刷？**

> 用 Bucket4j 令牌桶，按 IP 每分钟 120 次，超限返回 429。过滤器里尝试消费 1 个令牌，失败直接返回，不进业务。
>
> 实测连续 125 次请求，约 99 次被 429 拦下。
>
> 不足是桶在 JVM 内存，多实例时每台各自限流；生产应该把桶放 Redis，或者在网关层统一限流。

---

### Q36. 怎么监控？

**面试官：线上出问题怎么定位？**

> Actuator 暴露 health、metrics、prometheus；Micrometer 采集 JVM、HTTP、连接池指标；MVT 瓦片有命中率 Gauge；`pg_stat_statements` 提供慢查询；Agent 有 monitor 和 trace。
>
> 可以从接口 P95、错误率、慢 SQL、瓦片命中率、Agent 工具失败率几个维度定位。

---

### Q37. 测试怎么分层？

**面试官：这个项目有测试吗？怎么测的？**

> 三层：JwtService 单测；Controller 用 MockMvc 测参数校验和权限；集成测试用 Testcontainers 起真实 PostGIS，测 `ST_DWithin`、物化视图这些 H2 模拟不了的东西。没有 Docker 时集成测试自动跳过。
>
> 当前 21 个自动化用例通过、1 个跳过；另外有 `scripts/test_30_cases.py`，30 个功能用例全部通过，覆盖查询、生活圈、路线、Agent、限流和 RBAC，并输出真实耗时报告。

**追问：为什么不用 H2？**

> H2 没有 PostGIS 的 `ST_DWithin`、GiST、`ST_Contains`，用它测过了也不能证明生产可用，所以用 Testcontainers 起真实 PostGIS。

---

### Q38. 怎么部署？

**面试官：这个项目能部署吗？**

> 能。Dockerfile 多阶段构建，docker-compose 起 app、postgres、redis、geoserver、prometheus、grafana；CI 用 GitHub Actions 跑 `mvn verify`。
>
> 当前是本机演示环境，压测也是单机 50 并发，不能代表生产容量。

## 第六轮 · 压力追问

### Q39. 这些数字都是你测的吗？

**面试官：简历上这么多数字，哪些是你实际测的？**

> 都是我在这台机器上实际跑的，测试脚本和报告在仓库里。
>
> 比如 690ms→54.6ms 是同一张 10M 表、同一条 SQL、删/建索引前后用 `EXPLAIN ANALYZE` 测的；220ms→0.024ms 是实时聚合和物化视图的对比；导入 14.7/6.8/9.8s 是 5 万行三种方式各跑一次；30 个功能用例和 P50/P95 在 `功能测试报告.md` 里。
>
> 我会注明单机环境、数据规模和测试方法，不会把合成数据或单机压测说成生产指标。

---

### Q40. 这个项目是你一个人做的吗？

**面试官：项目是独立完成还是团队？参考了哪些开源项目？**

> 代码、数据脚本、测试和文档是我独立完成的；Agent 的目录结构参考了 EchoMind 的分层思路，但按实习项目做了精简，没有照搬它的 MCP、ChromaDB、多 Agent 并行这些复杂模块。

---

### Q41. 为什么用 Spring JDBC，不用 MyBatis/JPA？

**面试官：为什么不用 MyBatis 或 JPA？**

> 因为空间 SQL 高度定制，`ST_DWithin`、`ST_AsMVT`、`pgr_ksp` 这些用 JdbcTemplate 写最直接，SQL 完全可控，也方便看执行计划。
>
> JPA 对 geometry 类型映射麻烦，还容易生成不理想的 SQL。如果团队统一用 MyBatis，也可以换，核心 SQL 不变。

---

### Q42. 项目最大的难点是什么？

**面试官：讲一个你印象最深的难点。**

> 我讲路网不连通。最早用 `pgr_dijkstra` 算路线，有些起终点直接返回 0 条边，一开始以为是 SQL 写错了，后来查出来是 OSM 路网存在断头和孤岛，起终点落在不同连通分量里。
>
> 解决分两步：先取最大连通分量 `road_main`，保证主干路网可达；步行场景再加 `road_walk_all` 回退，并对快速路和主干道加成本惩罚。之后路线接口就稳定了。
>
> 这个问题的教训是：图算法的输入不是天然连通的，数据质量要先处理。

---

### Q43. 项目有哪些不足？

**面试官：你觉得这个项目还有什么不足？**

> 我列几个主要的：会话记忆在内存，重启丢失，应该换 Redis；生活圈是欧氏半径，不是路网等时圈，下一步用 `pgr_drivingDistance`；人口网格 1km 比较粗，可以换 100m constrained；并发导入的 staging 是全局清空，会互相踩；压测是单机 50 并发，不代表生产；权限用户还是内存演示账号；Valhalla 用公共实例，生产要自建。

**追问：下一步怎么改？**

> 优先做三件事：记忆迁移到 Redis；生活圈接路网等时圈；导入按 taskId 隔离 staging。这三个都是当前架构下能落地、收益明确的改进。

---

### Q44. 如果重做一次，你会怎么改？

**面试官：如果重新做这个项目，你会有什么不同？**

> 第一，先定评估口径再做功能，比如生活圈一开始就明确“欧氏还是路网”，避免后面解释成本。
>
> 第二，更早引入集成测试和测试数据，尤其是空间 SQL，越晚补越难。
>
> 第三，Agent 的工具系统一开始就统一到 ToolRegistry，不保留第二套循环。
>
> 第四，性能和成本指标从第一天就记录，避免最后回头补数字。

### Q45. 为什么投这个岗位？项目和岗位怎么匹配？

**面试官：你为什么做这个项目？和你投的 GIS 后端/空间数据岗位有什么关系？**

> 我投的是 GIS 后端和空间数据方向，这个项目覆盖了岗位最常见的四类能力：空间数据库建模与索引、空间查询与分析、地图服务和瓦片、以及把空间能力包装成 Agent 和业务接口。
>
> 数据侧我练了 PostGIS、投影、GiST、物化视图；工程侧练了 Spring Boot、缓存、异步、安全、监控、测试；分析侧练了生活圈和多路线。这些都能直接迁移到岗位里的 POI、选址、路径、区域统计类需求。
