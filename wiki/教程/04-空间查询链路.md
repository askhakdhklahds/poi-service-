# 04 空间查询链路

## 目标

能讲清一个 `/api/poi/within` 请求从 Controller 到 PostGIS 再回到 JSON 的全过程。

## 入口

`controller/PoiController.java`：

```java
@GetMapping("/within")
public Map<String, Object> within(
        @RequestParam double lon,
        @RequestParam double lat,
        @RequestParam(defaultValue = "1000") int radius,
        @RequestParam(required = false) String category,
        @RequestParam(defaultValue = "200") int limit) {

    validate(lon, lat);
    int safeRadius = Math.min(Math.max(radius, 1), 50000);
    int safeLimit = Math.min(Math.max(limit, 1), 500);
    ...
}
```

Controller 只做三件事：接参、校验、夹范围。

## 核心 SQL

`service/PoiService.java` 的 `within`：

```sql
WITH p AS (
  SELECT ST_Transform(ST_SetSRID(ST_MakePoint(?, ?), 4326), 4549) AS pt
)
SELECT id, name, category, sub_category,
       ROUND(ST_Distance(geom_4549, p.pt)) AS distance_m,
       ST_X(geom) AS lon, ST_Y(geom) AS lat,
       ST_AsGeoJSON(geom) AS geojson
FROM poi, p
WHERE ST_DWithin(geom_4549, p.pt, ?)
ORDER BY distance_m
LIMIT ?;
```

三个关键点：

1. **只转参数点一次**，不对表列做 `ST_Transform`。
2. `ST_DWithin` 能用 GiST 做包围盒预筛。
3. 半径/limit 夹范围，防止拖库。

## 最近邻

```sql
ORDER BY geom_4549 <-> p.pt LIMIT ?;
```

`<->` 是 GiST 距离算子，走 KNN 索引，只读最近 N 行。

## 点面归属

```sql
SELECT p.id, p.name, d.name AS district_name
FROM poi p
LEFT JOIN district d ON ST_Contains(d.geom, p.geom)
WHERE p.id = ?;
```

## 完整链路

```
浏览器
  → RateLimitFilter
  → Spring Security
  → PoiController.within
  → PoiService.within
  → JdbcTemplate
  → PostgreSQL/PostGIS
  → List<Map>
  → Jackson
  → {"code":0,"message":"ok","data":[...]}
```

## 面试问答

**Q：为什么用 ST_DWithin，不用 ST_Distance < x？**

A：`ST_DWithin` 能用 GiST 做 MBB 粗筛，`ST_Distance < x` 必须逐行精算，无法走索引。10M 数据 690ms vs 54.6ms。

**Q：为什么先转参数点？**

A：参数只有一行，转一次即可；对 `geom` 列做 `ST_Transform` 会让每行都算，且索引失效。

**Q：`within` 为什么按 `distance_m` 排序，`nearest` 用 `<->`？**

A：`within` 已经用半径过滤，结果集有限，可以按精确距离排序；`nearest` 不设半径，用 KNN 索引取最近 N 个更高效。
