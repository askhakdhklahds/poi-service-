# 05 物化视图与缓存

## 目标

能解释“220ms → 0.024ms → 接口 25ms”这条链路。

## 问题

行政区统计要：

```sql
SELECT d.adcode, d.name, count(p.id)
FROM district d
LEFT JOIN poi p ON ST_Contains(d.geom, p.geom)
GROUP BY d.adcode, d.name;
```

10M 数据实时算约 220ms。

## 物化视图

```sql
CREATE MATERIALIZED VIEW mv_district_stats AS
SELECT d.adcode, d.name, count(p.id) AS poi_cnt
FROM district d
LEFT JOIN poi p ON ST_Contains(d.geom, p.geom)
GROUP BY d.adcode, d.name;
```

把“点面归属 + 聚合”提前算好，存成 16 行。

- 实时聚合 220ms → 物化视图 0.024ms。
- 全量构建 4 分 6 秒。
- `REFRESH MATERIALIZED VIEW CONCURRENTLY` 不锁读，但需要唯一索引。


| 层 | 作用 | 效果 |
|---|---|---|
| Redis `@Cacheable` | 减少数据库访问 | 接口 58ms → 25ms |
| 物化视图 | 减少数据库计算 | 220ms → 0.024ms |
| 实时 JOIN | 兜底 | 物化视图缺失时仍可用 |

## 刷新

`controller/AdminController.java`：

```java
String exists = jdbc.queryForObject(
    "SELECT to_regclass('public.mv_district_stats')::text", String.class);
if (exists == null) {
    // 创建物化视图 + 唯一索引
} else {
    jdbc.execute("REFRESH MATERIALIZED VIEW CONCURRENTLY mv_district_stats");
}
cacheManager.getCache("districtStats").clear();
```

刷新策略：导入后、定时任务、低峰手动触发。

## 面试问答

**Q：物化视图算作弊吗？**

A：不算，是典型空间预聚合；代价是刷新慢，适合定时/低峰刷新。

**Q：为什么有了物化视图还要 Redis？**

A：物化视图减少数据库计算，Redis 减少数据库访问，是两层不同的问题。

**Q：`CONCURRENTLY` 的前提？**

A：物化视图上要有唯一索引；它不锁读，但刷新更慢、需要额外空间。
