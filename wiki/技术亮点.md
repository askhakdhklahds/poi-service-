# 技术亮点

## 1. 双列坐标模型：4326 存储 + 4549 米制计算

**问题**：4326 的单位是“度”，直接算距离会得到无意义的度数；每次查询 `ST_Transform` 又会让索引失效。

**做法**：

- `geom geometry(Point,4326)`：交换、展示、点面归属。
- `geom_4549 geometry(Point,4549)`：CGCS2000 3 度带，单位米。
- 两列都建 GiST。

**效果**：`ST_DWithin` 直接走索引；10M 数据从 690ms 降到 54.6ms（2026-11-16 复测：无索引约 1.19s，索引热缓存 24–139ms，中位约 27ms）。

**面试一句话**：不是“存两份浪费”，而是“一份负责交换、一份负责计算”。

## 2. GiST + ST_DWithin：让周边查询走索引

**问题**：`ST_Distance(geom, pt) < 1000` 必须逐行精算，无法走索引。

**做法**：用 `ST_DWithin`，GiST 先按最小外接矩形粗筛，再精确判断。

**效果**：10M 数据 `ST_DWithin` 无索引 690ms → GiST 54.6ms（冷）/ 约 22ms（热）；反例 `ST_Distance < 1000` 879ms。

**面试追问**：为什么热缓存 22ms、接口 P95 50.9ms？因为接口还有 `ST_AsGeoJSON`、JSON 序列化、网络与连接开销。

## 3. KNN `<->`：最近邻不排序全表

**做法**：`ORDER BY geom_4549 <-> pt LIMIT N`，GiST 提供距离排序算子。

**效果**：10M 数据 0.37ms，Index Scan，只读最近 N 行。

## 4. 物化视图 + Redis：统计从 220ms 到 0.024ms

**问题**：行政区统计要 `ST_Contains` + 聚合，10M 数据实时算 220ms。

**做法**：

- 物化视图 `mv_district_stats` 预聚合 16 行。
- `REFRESH MATERIALIZED VIEW CONCURRENTLY` 刷新，需要唯一索引。
- 接口层 `@Cacheable` 写 Redis，TTL 5 分钟。

**效果**：SQL 220ms → 0.024ms；接口冷启动 58ms → Redis 命中 25ms。（2026-11-16 复测：实时聚合热缓存 73–76ms、物化视图 0.014ms，冷启动约 0.76s。）

**面试一句话**：物化视图减少数据库计算，Redis 减少数据库访问，是两层不同的问题。

## 5. MVT：地图体积降 75%~79%

**做法**：

- `ST_TileEnvelope` 算瓦片范围。
- `ST_Intersects` 用 4326 GiST 粗筛。
- `ST_AsMVTGeom` 转瓦片坐标并裁剪。
- `ST_AsMVT` 编码 Protobuf。
- Caffeine 缓存 `z/x/y/category`。

**效果**：真实数据 227KB → 49.7KB（降 78.6%）；10M 数据 3387KB → 856KB（降约 75%）。

**面试追问**：MVT 为什么小？只返回视口数据 + 二进制编码 + 属性名只存一次。

## 6. 异步导入：COPY + staging + 幂等

**做法**：

- 上传后立即返回 taskId，`@Async("importExecutor")` 后台跑。
- `COPY` 快速进 `poi_staging`。
- 一条 `INSERT ... SELECT` 生成几何、转投影、校验、`ON CONFLICT DO NOTHING`。

**效果**：5 万行逐条 14.7s、Batch 6.8s、COPY+staging 9.8s。（2026-11-16 复测：逐条 11.3–16.3s、Batch 3.9–4.2s、COPY 2.7s；结论依赖缓存与转换开销，核心是批量远快于逐条。）

**面试口径**：COPY 不是永远最快；这里多了一次 staging → 正式表的转换。批量远快于逐条，这是核心结论。

## 7. EchoMind 风格 Agent：分层、可解释、可回退

**问题**：早期 Agent 逻辑集中在 `AgentService`，LLM、规则、工具、记忆混在一起，不好讲也不好改。

**做法**：

- `AgentOrchestrator`：意图 → 路由 → 执行 → 校验 → 汇总。
- `IntentRecognizer`：关键词 + 可选 LLM。
- `AgentProfiles` + `profiles.json`：角色契约配置化。
- `BaseAgent` + 4 个角色：General / SpatialQuery / RoutePlanning / Report。
- `ToolRegistry`：白名单、必填参数、超时、统计。
- `ConversationStore`：多轮记忆 + 追问改写。
- `AnswerVerifier`：空答案、无工具证据、异常数值。
- `TraceStore` / `AgentMonitor`：工具轨迹、成功率、耗时。

**设计原则**：LLM 负责理解与表达，空间计算交给确定性 SQL 工具；规则/工具失败时仍有兜底。

**面试一句话**：这不是“接了个大模型”，而是“把 Agent 拆成可路由、可工具、可校验、可观测的工程结构”。

## 8. 15 分钟生活圈：从“有什么”到“够不够”

**问题**：原来的 POI 平台只能回答“附近有什么”，不能回答“这个区的居民 15 分钟内能不能到、覆盖多少人、哪里是盲区”。

**做法**：

- WorldPop 1km 人口栅格 → `population_grid`（15,237 个网格，9,422 个落在区内）。
- 按七普总人口 24,870,895 统一校准。
- `ST_DWithin` 计算每个网格是否被设施覆盖，按人口加权汇总。
- 输出覆盖率、覆盖人口、盲区人口、网格 FeatureCollection。
- 页面支持行政区/设施/5-10-15 分钟切换。

**实测示例**：

| 区域 | 设施 | 覆盖率 | 覆盖人口 | 盲区人口 |
|---|---|---|---|---|
| 黄浦区 | 医疗 | 97.2% | 658,413 | 19,060 |
| 黄浦区 | 教育 | 76.7% | 519,353 | 158,120 |
| 浦东新区 | 医疗 | 31.9% | 1,711,833 | 3,647,388 |
| 浦东新区 | 教育 | 20.5% | 1,097,548 | 4,261,673 |

**面试一句话**：这把项目从“空间查询 Demo”提升成了“能支撑公共服务设施评估的空间分析工具”。

## 10. 多路线对比：车/人两套路网 + 沿途特点

**问题**：原路线是“从起点出发访问多个景点”的贪心排序，不是 A→B 的多方案对比，也没有车/人区分。

**做法**：

- **首选 Valhalla 高精度路网**：`ValhallaRouteService` 调公共 `/route`，`costing=auto|pedestrian`，支持备选路线与 polyline6 几何；返回 `sourceLabel=高精度路网`。
- **本地兜底**：`road_car`（maxspeed/等级算时间，oneway 控方向）、`road_walk_v2`（排除 path/track，优先人行道/居住区）、`road_walk` / `road_walk_all` 回退。
- `externalOrLocal`：Valhalla 为空/超时/异常时自动回退 `pgr_ksp`，接口不中断（8s 超时）。
- `pgr_ksp` 取多条候选，按边集合 Jaccard 去重。
- 每条路线统一用本地 PostGIS 统计距离、时间、道路类型构成、150m 缓冲内 POI、经过行政区。
- 前端 `route.html` 多色绘制，点击卡片高亮路线，卡片显示来源标签。
- 路线页支持**地名输入自动定位**：防抖调用 `/api/poi/search`（POI + 行政区），下拉选择后打点并自动规划，不再只能在地图上点选。

**实测**：人民广场→外滩，Valhalla 驾车 2.9km/11min、步行 2.0km/27min，3+3 条路线；接口冷启动 1.1–2.3s，Redis 命中约 60ms。本地兜底外滩→陆家嘴 3+3 条。

**面试一句话**：路线质量靠“外部高精度路网 + 本地空间富化 + 失败自动降级”组合，而不是自己硬拼一套不完整的 OSM 路网。

## 11. 前端可视化与可解释性

**问题**：底图高缩放出现 “Map data not yet available”；POI 全部同色；Agent 秒回让人怀疑没调用。

**做法**：

- 底图切到 `World_Imagery`，`maxZoom=18`；高德页面 `maxzoom=18`。
- 8 类 POI 分类配色 + 图例。
- Agent 显示 intent/agentType/engine/toolsUsed/latencyMs，执行轨迹默认展开，提供 trace link。
- POI 显隐开关：`all-tiles.html` 和 `agent.html` 都提供。
- 首页五个入口改成快捷卡片，空间助手重新设计。
- 生活圈绿色/红色网格、多路线多色线条。

**效果**：z18 加载 30 张影像瓦片；Agent 22ms 显示 2 个工具；生活圈 34 个可见网格；截图 `shot_agent_ui.png` / `shot_basemap_z18.png` / `shot_life_circle_cdp.png` / `shot_route_cdp.png`。

**面试一句话**：Agent 秒回不是没调用，而是走了确定性 SQL 工具；UI 把 intent、工具、耗时和轨迹都暴露出来了。

## 12. 如实说的不足

- 生活圈 MVP 用欧氏半径，不是路网等时圈；下一步接 `pgr_drivingDistance`。
- WorldPop 1km 旧版是未约束估计，已按七普总人口校准；更高精度应换 100m constrained 数据。
- 会话记忆在内存，重启丢失；生产应换 Redis + TTL。
- 导入的 `TRUNCATE poi_staging` 是全局的，并发导入会互相踩。
- 压测是单机 50 并发，不代表生产容量。
- 权限用户是内存演示账号，未接数据库/LDAP。
